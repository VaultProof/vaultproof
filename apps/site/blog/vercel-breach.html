How Vercel got breached through
a third-party AI tool.

Attackers didn't break through Vercel's firewall. They walked through an OAuth door that a compromised AI tool left open. API tokens, NPM secrets, GitHub credentials, and 580 employee records were exfiltrated before Vercel knew anything was wrong. Here's the full attack chain — and why every team using Vercel should be rotating secrets right now.

01 — What happened

One OAuth token.
Full internal access.

On April 19, 2026, Vercel confirmed that threat actors had gained unauthorized access to certain internal systems. The public disclosure came after attackers posted on dark web forums claiming they were in possession of Vercel's internal data and were selling access.

The attack didn't exploit a zero-day in Vercel's infrastructure. It didn't involve a phishing campaign against Vercel employees. Instead, it exploited something far more insidious: a small third-party AI tool that Vercel had integrated into its internal workflows — and that tool's Google Workspace OAuth application had been compromised in a broader supply chain attack affecting hundreds of organizations.

When the AI tool's OAuth app was compromised, so was every organization that had granted it access. For Vercel, that meant attackers inherited an OAuth token with legitimate access to internal systems. No brute force. No malware dropped on an endpoint. Just a valid access token — walking through the front door.

Critical finding

The initial OAuth compromise affected hundreds of organizations across many industries. Vercel was one of many victims — but one of the highest-profile, given that its internal systems contain the deployment secrets and source code of millions of developers.

02 — What was taken

The exfiltrated data.

According to threat actor claims — which Vercel has not fully confirmed or denied on a line-by-line basis — the stolen data encompasses everything you'd expect an attacker to want from a deployment platform: the keys to your infrastructure, and the code running on it.

Credentials & tokens

  • Vercel API access keys
  • NPM publish tokens
  • GitHub OAuth tokens
  • Internal service credentials
  • Environment variables (non-sensitive)

Internal systems access

  • Linear project management data
  • User management system records
  • Internal deployment configurations
  • Source code repositories

Personnel data

  • 580 employee records
  • Names and Vercel email addresses
  • Account status flags
  • Activity timestamps

Scope (per Vercel)

  • "Limited subset" of customers affected
  • Deployment platform itself not impacted
  • Sensitive env vars (marked) not exposed
  • Active investigation ongoing
Important nuance

Vercel distinguishes between "sensitive" environment variables (those explicitly marked in project settings) and standard ones. Only non-sensitive environment variables are considered potentially exposed. If your team didn't mark secrets as sensitive, assume they were in scope.

NPM tokens deserve special attention. A compromised NPM publish token means an attacker could silently push malicious versions of packages. Given how many developers install Vercel-adjacent packages in their build pipelines, a poisoned NPM package from Vercel's registry would be a devastating second-stage attack. There is currently no evidence this occurred — but it illustrates the cascading blast radius of deployment platform breaches.

03 — How it happened

The OAuth trust problem.

The attack vector here is increasingly common and deeply underappreciated: OAuth supply chain compromise. Your organization doesn't get breached — a tool you authorized gets breached, and its access token becomes the attacker's credential.

The typical OAuth integration flow looks benign. A productivity tool, an AI assistant, a CI/CD helper — they all request access to your Google Workspace, Slack, or GitHub. You review the permission scopes. You click "Allow." The tool works as advertised, for months or years. Then the tool's OAuth app gets compromised, and every organization that granted it access is now exposed.

The OAuth attack model how access was inherited 
# Normal OAuth authorization (what Vercel's team did)
authorize("ai-tool.io", scopes=["read:internal", "read:calendar"])
# → token stored in ai-tool.io's infrastructure
# → ai-tool.io gets breached
# → attacker retrieves token

# Attacker's perspective (no brute force needed)
GET https://internal.vercel.com/api/data
Authorization: Bearer eyJhbGciOiJSUzI1...  # valid token, stolen from third party
# → 200 OK. You're in.

The attacker never needed to touch Vercel's perimeter. They exploited a trust relationship that Vercel had intentionally established. From the internal system's perspective, every request looked legitimate — it came with a valid, non-expired token issued by a real Google OAuth flow.

"The breach wasn't at Vercel's perimeter. It was at the perimeter of a tool Vercel trusted."

This is why OAuth supply chain attacks are so dangerous: the victim organization's defenses are entirely irrelevant. You can have MFA on every account, encrypted disks, zero-trust networking — and still be fully exposed if a third-party tool with access to your systems gets compromised upstream.

Why this will keep happening

The AI tool integration wave has dramatically expanded the OAuth attack surface for every organization. Teams are authorizing dozens of AI assistants, automation tools, and productivity apps — each holding a token into internal systems. Most of these tools are small companies with lean security teams. They are high-value targets because compromising one tool yields access to hundreds of enterprise customers.

ShinyHunters — the group most publicly associated with this breach, though they have denied specific involvement — has operated precisely this model before: compromise a cloud platform or SaaS tool, extract all the stored OAuth tokens and API credentials, then enumerate which victims are worth targeting. Vercel, with its deep hooks into developer infrastructure worldwide, was an obvious high-value target.

04 — Why platform secrets failed

Vercel's own vault.
Raided.

Vercel's environment variable system is, for most developers, their de-facto secrets manager. You push a key to Vercel's dashboard. Vercel encrypts it and injects it at build or runtime. It never appears in your codebase. It feels secure.

The problem is structural: the entity storing your secrets is the same entity that was breached. When Vercel's internal systems were accessed, the attacker had access to the same internal APIs and data stores that Vercel uses to inject environment variables into deployments. The secrets were at rest in a system the attacker was now inside.

Root cause

Storing secrets inside a deployment platform means your secret's security is bounded by that platform's security. If the platform is breached, your secrets are in scope — regardless of what encryption they use at rest, because the attacker has access to the same privileged context that would decrypt them.

This is the fundamental architectural flaw that platform-stored secrets cannot solve: they're only as secure as the platform holding them. Not the encryption algorithm. Not the key derivation function. The platform itself — its internal tooling, its employees' access, and every third-party OAuth integration it authorizes.

What "mark as sensitive" actually means

Vercel's guidance following the breach was to ensure secrets are marked as "sensitive" in project settings. Sensitive environment variables are handled with additional access controls — they're not returned by certain API endpoints and require explicit privilege to read. This is meaningful protection in normal operations.

But in a breach scenario where the attacker has access to internal systems with elevated privileges, the sensitive/non-sensitive distinction may provide less protection than advertised. An attacker operating inside privileged internal infrastructure may be able to access what normal API calls cannot. We don't yet know the full scope of what was accessed.

05 — What would have stopped it

The architectural
answer to platform breaches.

The Vercel breach is a clear illustration of why "the platform stores your secrets securely" is an incomplete security model. There is one architectural principle that does hold regardless of platform breach status: secrets that never reach the platform cannot be exfiltrated from the platform.

The approach: split secrets client-side before they're ever transmitted. Using cryptographic secret sharing (Shamir's scheme, for example), a secret key is divided into shares at the developer's machine. No complete key is ever transmitted to or stored in any single system. The platform stores only a share — useless without the other half held elsewhere.

Platform-stored secret (vulnerable model) compromised in breach 
# Developer sets secret in Vercel dashboard
OPENAI_API_KEY=sk-proj-abc123...  # stored whole in Vercel's vault

# Vercel gets breached
# Attacker reads internal API → gets OPENAI_API_KEY directly
# Result: your OpenAI account is now theirs
Split-secret model (breach-resistant) nothing recoverable from platform breach 
# Developer's machine: key is split before upload
[share_1, share_2] = shamir_split(sk-proj-abc123...)

# Share 1 → encrypted, stored in vault (Vercel env var or otherwise)
# Share 2 → encrypted with developer's key, stored separately
VAULTPROOF_SHARE=enc:a9f2c...  # useless without share_2

# Vercel gets breached
# Attacker reads VAULTPROOF_SHARE → cryptographic noise, no usable secret
# Result: your API keys are safe

This model doesn't require Vercel to be secure. It doesn't require you to audit every OAuth integration your deployment platform has authorized. It provides a guarantee that's independent of the platform's security posture: a single storage location cannot yield a usable secret.

Key insight

The goal isn't to find a platform that won't be breached. Every platform is breachable. The goal is to ensure that a breach of the platform yields nothing of value to an attacker. Split-secret architecture achieves this for API keys and credentials.

06 — What to do now

Your immediate
action list.

If you use Vercel and have environment variables stored there, treat this as a notification that your secrets may have been exposed. Act accordingly.

Immediate (today)

Rotate everything stored in Vercel. OpenAI keys, Stripe secrets, database connection strings, webhook secrets, third-party API tokens — rotate all of them. This is not optional if you care about your users' data. Start with the keys that have write or billing access.

Audit your OAuth integrations. Check what third-party apps and AI tools have OAuth access to your internal systems — Google Workspace, GitHub, Slack, Notion, Linear. For anything you don't actively use or can't verify is uncompromised, revoke access immediately. Reconnect only what you need.

Check for anomalous API activity. Review your API provider dashboards (OpenAI, Stripe, AWS, etc.) for unexpected usage in the past week. Look at request volumes, unusual times, unfamiliar IPs, requests for resources your app doesn't normally touch.

This week

Implement least-privilege for environment variables. Every secret should be scoped as narrowly as possible. Read-only DB connection where read-only suffices. Resource-scoped API tokens, not root-level keys. This limits blast radius when (not if) a platform storing your secrets is next breached.

Move sensitive secrets off platform-native storage. If your architecture depends on Vercel (or any deployment platform) as your primary secrets vault, this breach is a clear signal to reconsider. Consider split-secret architectures, or at minimum, hardware-backed secret management where secrets are not accessible to the platform's own internal systems.

Enable secret scanning on your repos. As a precaution, ensure your codebase and commit history don't contain any hardcoded secrets that might have been in scope during the breach window.

On Vercel's response

Vercel has engaged external incident response teams, notified law enforcement, and published a security bulletin — the standard responses a well-run company makes in this situation. The root cause is architectural, not operational negligence. The lesson for teams using Vercel isn't to stop using it; it's to not treat it as a secrets vault.
