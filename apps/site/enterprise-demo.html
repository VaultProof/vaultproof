Architecture

Show the security boundary in one screen.

Enterprise buyers want to know where the raw key can exist, who can call it, and how quickly misuse can be stopped. This section makes that visible immediately.

Before
OPENAI_API_KEY=sk-proj-...
Lives in `.env`, CI variables, shell history, agent context, or config screens.
Any compromised app server, repo leak, browser bundle mistake, or pipeline compromise can use the raw credential immediately.
Incident response is usually “rotate everything and hope you found all copies.”
After VaultProof
VAULTPROOF_PROJECT_ID=vp-proj-enterprise
OPENAI_BASE_URL=https://init.vaultproof.dev/p/openai/v1
Policy
Enforce origin lock, IP rules, provider restrictions, and caps before forwarding upstream.
Audit
Log which project, which route, which provider, and when each call happened.
Response
Revoke instantly without searching every codebase, repo, or device config.
Talk Track

VaultProof does not replace your vault. It changes what your app receives at runtime. Instead of pulling the raw third-party secret into the app, pipeline, or device-facing service, you route calls through a policy layer that keeps the provider key off those surfaces.

Show where the same model works.

This is the strongest part of the enterprise story: once you sell the runtime boundary, the same control model can cover web apps, internal agents, CI/CD, and connected systems.

Web App Pattern

Browser and backend share one policy-controlled path.

For SaaS teams, the cleanest motion is to replace raw provider secrets in the backend and origin-lock browser traffic. That makes leaked front-end identifiers much less dangerous and gives the security team a visible boundary around outbound API usage.

Lock calls to your production origin and selected API routes.
Use the same provider SDK with a rewritten base URL.
Track usage, errors, and revoke events in a shared dashboard.

Pilot Plan

A realistic enterprise rollout in 30 days.

Week 1: pick one high-risk integration

Choose the AI provider, payment flow, or CI job that currently depends on a plaintext third-party key.

Week 2: route through VaultProof

Run the init flow, replace the provider secret with a project ID, and apply origin or IP policy for that path.

Week 3: validate logs, alerts, and revoke flow

Walk security through the audit view, rate controls, spend caps, and incident response story.

Week 4: expand to the next environment

Move from one app to the next, or from staging into CI/CD, browser-origin traffic, or edge gateway traffic.
