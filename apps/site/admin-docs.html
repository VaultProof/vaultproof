Admin-only guide

Customer support playbook for VaultProof admins.

Use this page when helping customers onboard, diagnose failed setup, check dashboard state, and collect safe troubleshooting details without asking for raw provider keys.

Support rules
  1. 1Never ask customers to send raw provider keys.
  2. 2Collect timestamps, provider names, env variable names, and request IDs.
  3. 3Use Activity Logs before assuming provider failure.
  4. 4Escalate with redacted output and account identifiers only.

Triage

Start with safe facts.

Before troubleshooting, gather enough context to find the account and the request path without exposing secrets.

Ask for

  • Customer email or workspace name.
  • Provider name and env variable name.
  • Hosting provider and environment.
  • Approximate timestamp and timezone.
  • Request ID from Activity Logs if available.

Do not ask for

  • Raw OpenAI, Stripe, Anthropic, GitHub, or other provider keys.
  • Full unredacted env files.
  • Production secrets exported from hosting providers.
  • Personal access tokens for GitHub or cloud accounts.

Onboarding

When setup does not finish.

Symptom Likely cause Admin action
CLI says no keys found The key is outside scanned env files, uses an unknown shape, or is a custom internal API. Ask for env variable names only. Have the customer run vaultproof-init custom for custom APIs.
Browser login did not complete Callback blocked, session expired, or customer used a different browser profile. Have them sign in to the app first, then rerun vaultproof-init. Check account exists in admin.
Local app still uses old key The process was not restarted or a different env file is loaded. Ask which env file the framework reads. Have the customer restart and confirm generated values are loaded.
Production fails but local works Hosting secrets were not updated, deployment is stale, or a raw key remains in production. Have the customer compare variable names in hosting secrets with the generated VaultProof block.
Helpful commands: For advanced diagnosis, ask the customer to run vaultproof-init doctor or vaultproof-init --dry-run and send redacted output.

Admin page

What to verify in the admin console.

Account and token state

Confirm the user account exists, the workspace is active, and the VaultProof token has protected keys attached. If a token was deleted, the customer must rerun init or create a new token.

Activity and alerts

Look for the timestamped request. If there is no request, the app is not reaching VaultProof. If there is a request with a provider error, troubleshoot provider config or limits.

Plan limits

Check protected key count, monthly calls, retention, and plan status. Rate limits or exhausted plan capacity can look like provider failures to the customer.

Scanner state

Confirm GitHub connection status, repository access, scan status, and any unresolved findings before advising customers to rotate or migrate keys.

Providers

Separate VaultProof routing from upstream provider failure.

Status Meaning Next step
No VaultProof log The customer app did not call VaultProof. Check env loading, deployment, base URL, and whether the customer restarted the app.
401 or 403 from provider The upstream provider rejected the reconstructed key or account permissions. Have customer rotate the provider key and update the protected key in VaultProof.
429 Rate limit from VaultProof plan or upstream provider. Check plan usage, provider quota, and burst behavior in Activity Logs.
5xx Provider or VaultProof upstream issue. Collect request ID, timestamps, provider, route, and account. Escalate if repeated.

Scanner

Helping customers with repository scans.

Repo is missing

Ask the customer to confirm GitHub installation permissions and whether the repo belongs to the selected organization. Do not request a GitHub token.

Finding looks wrong

Review provider, file path, line number, and masked value. If it is a false positive, the customer can ignore it. If it is real, guide rotation first.

Migration PR failed

Check branch protection, repository write permissions, and whether the GitHub app can create branches and pull requests.

Customer already rotated

Have them mark the finding resolved after confirming the old key is revoked at the provider and no new calls use it.

Escalation

What to include when handing off.

  • Customer account email and workspace identifier.
  • VaultProof token ID or masked token prefix.
  • Provider, route, endpoint, request ID, and timestamps.
  • Plan state and relevant usage numbers.
  • Redacted CLI output from vaultproof-init doctor or --dry-run.
  • Whether the issue reproduces locally, in production, or both.
Secret handling: If a customer accidentally sends a raw provider key, tell them to rotate it immediately at the provider and replace the protected key in VaultProof.
